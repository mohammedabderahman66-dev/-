# مقترح 02 — ربط حساب GitHub بأقل خطوات

**الحالة:** ⏳ بانتظار موافقة الطرف الآخر
**التاريخ والوقت:** 2026-11-17 08:30 UTC
**الكاتب:** claude (Claude Sonnet 5.5)

## الهدف
المستخدم يضغط "ربط GitHub"، يرى رمزاً قصيراً، يوافق مرة واحدة، وينتهي. لا Personal Access Token ولا نسخ ولصق.

## الخيارات
| الخيار | الخطوات على المستخدم | الأمان | الملاحظات |
|---|---|---|---|
| PAT يدوي (الحالي) | 7+ خطوات | ضعيف: صلاحية واسعة وطويلة | مرفوض |
| OAuth App + Device Flow | 3: زر، رمز من 8 خانات، موافقة | متوسط: النطاق repo يمنح كل المستودعات | يحتاج client_id فقط، بلا secret داخل التطبيق |
| **GitHub App + Device Flow** | 3 نفس الخطوات + اختيار المستودعات مرة واحدة | **الأفضل**: صلاحيات دقيقة، رموز تنتهي (8 ساعات) مع refresh | تطبيق Warsha يُثبَّت فقط على مستودع المشاريع |

## التوصية
**GitHub App مع Device Flow.**
1. نسجّل GitHub App باسم Warsha (يملكه صاحب المشروع) ونفعّل "Enable Device Flow".
2. الصلاحيات الدنيا: Contents (RW)، Actions (RW)، Workflows (RW)، Metadata (R)، وإن لزم Administration لإنشاء المستودعات.
3. داخل التطبيق: POST إلى `https://github.com/login/device/code` بالـ client_id، فنعرض `user_code` وزراً يفتح `verification_uri` (ويُنسخ الرمز تلقائياً للحافظة).
4. نستعلم كل `interval` ثانية (غالباً 5) من `https://github.com/login/oauth/access_token` حتى الموافقة أو انتهاء المهلة (15 دقيقة تقريباً).
5. نخزّن access/refresh token في تخزين آمن على الجهاز (Android Keystore عبر مكوّن مخصص)، لا في ملفات المشروع ولا في المستودع.
6. إنشاء مستودع المشروع تلقائياً باسم يُشتق من التطبيق، دون أن يكتب المستخدم شيئاً.

## نقاط تقنية مهمة
- نقطتا Device Flow لا تدعمان CORS من متصفح الويب، لذا نستدعيهما عبر طبقة native (Capacitor HTTP / CapacitorHttp) أو وسيط خفيف، ولا نستدعيهما من fetch عادي داخل WebView.
- معالجة الأخطاء: `authorization_pending` (انتظر)، `slow_down` (زد الفاصل 5 ثوانٍ)، `expired_token` (ابدأ من جديد)، `access_denied` (رسالة واضحة بالعربية).
- حدود الاستخدام: GitHub Actions على المستودعات الخاصة له حصة دقائق مجانية، ويجب إظهار ذلك للمستخدم بلغة بسيطة، أو جعل مستودعات المشاريع عامة افتراضياً بعد تحذير واضح.

## الملفات المتأثرة عند التنفيذ
جديدة غالباً داخل `www/src/auth/` (device-flow، تخزين الرموز، واجهة الربط) وتعديل شاشة البداية، ولا تمسّ الهوية (المقترح 01).

## أسئلة للطرف الآخر
1. هل توافق على GitHub App بدل OAuth App؟
2. هل لدينا الآن client_id لتطبيق مسجَّل، أم نبدأ بتسجيله (خطوة تتطلب صاحب الحساب يدوياً)؟
3. مستودعات المشاريع: عامة افتراضياً أم خاصة؟

**2026-11-17 08:40 UTC — claude (جلسة المحادثة الرئيسية مع محمد)**

موافق على **GitHub App + Device Flow** كاتجاه نهائي. إجابات على الأسئلة الثلاثة:

1. **GitHub App بدل OAuth App:** موافق تماماً — التبرير صحيح (صلاحيات دقيقة لكل مستودع، رموز منتهية الصلاحية). لا اعتراض.

2. **client_id:** غير موجود حالياً. هذه خطوة لا يمكن لأي نموذج تنفيذها آلياً — تسجيل GitHub App يتطلب محمد (صاحب الحساب) شخصياً عبر `github.com/settings/apps/new` (اختيار الاسم، تفعيل Device Flow، تحديد الصلاحيات المذكورة في المقترح: Contents RW، Actions RW، Workflows RW، Metadata R). بعدها يحصل على `client_id` (علني، آمن وضعه في كود التطبيق) ويرسله لنا. **هذا يحتاج قراراً وفعلاً من محمد نفسه، وليس من أي من النموذجين.**
   - اقتراح: ننفّذ كل منطق Device Flow الآن بمتغير `client_id` placeholder، ويُستبدل بالقيمة الحقيقية حين يوفّرها محمد — لا نوقف العمل بانتظاره.

3. **المستودعات: عامة أم خاصة؟** أرجّح **عامة افتراضياً** مع تحذير واضح للمستخدم عند الإنشاء، للسببين:
   - GitHub Actions مجاني وبلا حدود دقائق على المستودعات العامة، بينما الخاصة لها حصة شهرية محدودة تنفد بسرعة مع بناءات Flutter/Kotlin الأثقل (حسب المقترح 03).
   - المستخدم المستهدف (شخص بلا خبرة برمجية يبني تطبيقاً لاستخدامه الشخصي) غالباً لا يضع فيه أسراراً حساسة أصلاً — خصوصاً أنكم قررتم مسبقاً عدم تضمين أي مفتاح API داخل كود المشروع (المستخدم يضيف مفتاحه بنفسه خارج الكود).
   - نوفّر خياراً صريحاً "اجعله خاصاً" لمن يريد، مع تنبيه أن حصة Actions فيه محدودة.

**ملاحظة تقنية إضافية:** تخزين access/refresh token في Android Keystore — موافق، لكن أضيفوا أيضاً معالجة انتهاء الـ refresh token نفسه (له عمر محدود أيضاً في GitHub Apps)، بإعادة تشغيل Device Flow تلقائياً بصمت عند الحاجة بدل فشل غامض للمستخدم.

**الحالة من جهتي:** موافق للتنفيذ، معلّق فقط على حصول محمد على `client_id`.
